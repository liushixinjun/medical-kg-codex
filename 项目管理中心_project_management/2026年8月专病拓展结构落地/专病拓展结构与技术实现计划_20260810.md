# P7 专病拓展结构与技术实现计划

> 目标：把“通用专科 Schema 能装下多数疾病”升级为“不同专病的特色内容可以被稳定表达、解析、入库、审计和 CDSS 使用”。

## 一、当前问题

前期 P7 只完成了通用结构复核，尚未完成专病特色结构验证。通用结构可以表达定义、症状、检查、诊断、治疗和证据，但遇到心肌病遗传/基因、肺动脉高压血流动力学、瓣膜病瓣膜部位和严重度、起搏治疗参数、心律失常电生理机制等内容时，如果没有明确扩展规则，后续解析会继续出现“能入库但不好用”的问题。

## 二、总体原则

1. 主结构不膨胀：疾病、症状、体征、检查、检验、药品、手术、治疗、诊断、证据等主结构继续保持稳定。
2. 专病差异走扩展槽位：只有教材、指南、共识或权威资料明确覆盖时，才启用对应扩展实体和关系。
3. 不建空壳节点：没有原文依据、没有临床用途、不能解释给医生看的，不生成节点。
4. 不影响 CDSS 标准字典：检查、检验、药品、手术、治疗项目仍优先对接 CDSS 标准字典；专病特色结构只补充临床语义，不替代标准字典。
5. 可审计、可复用：每个扩展项必须能追溯来源、适用疾病、使用场景和是否进入正式推荐链路。

## 四、技术实现方案

### 1. 建立专病扩展槽位配置

新增配置文件，按疾病大类定义允许启用的扩展槽位。解析脚本只能从配置中读取允许项，不能临时自由造结构。

建议文件：

- `公共执行层_kg_pipeline/专病扩展槽位配置.yaml`

配置内容包括：

- 疾病大类
- 可启用扩展实体
- 可启用关系
- 必须来源类型
- 是否允许进入正式推荐链路
- 是否必须映射 CDSS 字典

### 2. 升级解析流程

PDF/教材解析分两层：

- 第一层：通用骨架抽取，继续覆盖定义、病因、症状、体征、检查、检验、诊断、鉴别、治疗、随访、预后、证据。
- 第二层：专病扩展抽取，只有命中配置槽位并找到原文依据时才抽取。

### 3. 升级本地审计

新增 P7 专病扩展硬闸门：

- 扩展实体是否有来源证据。
- 扩展实体是否被疾病或推荐链路引用。
- 扩展实体是否误当成普通症状、检查、药品、手术。
- 扩展实体是否越权进入正式 CDSS 推荐。
- 扩展实体是否需要 CDSS 标准字典身份。

### 4. 升级入库后复核

Neo4j 入库后复核必须输出：

- 每个疾病启用了哪些专病扩展槽位。
- 哪些槽位有数据。
- 哪些槽位因资料未覆盖而为空。
- 哪些槽位进入正式推荐链路。
- 哪些槽位只用于知识展示。

### 5. 升级前端和 CDSS 使用说明

前端不需要理解所有内部字段，只按两层展示：

- 通用诊疗内容：临床表现、诊断检查、治疗方案、证据链。
- 专病特色内容：遗传/基因、血流动力学、瓣膜严重程度、心电分型、设备参数等。

正式 CDSS 推荐仍以“推荐陈述、推荐动作、触发条件、禁忌/排除条件、主证据”为核心，不直接把扩展实体当医嘱。
